01Anthropic закрыла IPO по $83

Разбор

  4. Вместе с публичным размещением и частным пакетом общая сумма до вычетов достигла $119,5 млрд.

03GPT-6.2 для части кибер-задач просит подтвердить личность

habr.comдоступно

вышли GPT-6.2 Astra и Sol, по программированию и сложным задачам сильнее. но для части кибербезопасных возможностей уже просят проверку личности, KYC. так что если берёшь в ChatGPT или Codex security-задачи, сначала гляди, нужна ли тебе верификация под такой доступ.

Разбор

Разработчик NetRuleRouter (открытое приложение на Rust) упёрся в фильтр Codex, когда перепроверял фикс утечки DNS, а до этого у него заблокировали платный Claude Max 20x после проверки личности. Отсюда его вопрос: не распространит ли OpenAI такие проверки на обычных разработчиков.

  1. По Preparedness Framework (внутренней шкале OpenAI для оценки рисков) Astra и Sol достигли уровня Critical по кибервозможностям.
  2. Программа Daybreak (Trusted Access for Cyber) делится на два уровня: Blue — защитная работа, аудит кода, анализ уязвимостей, расследование инцидентов и проверка исправлений; Red — продвинутые исследования, авторизованный пентест и эксплойты, и одобряют его строже, в первую очередь для организаций.
  3. Для индивидуальной заявки на Daybreak нужны платная подписка, возраст от 18 лет, Advanced Account Security и минимум один FIDO2-ключ, физический ключ для подтверждения входа.
  4. Без проверки личности модели доступны, но с более жёсткими ограничениями, а меньше отказов в кибер-задачах можно получить только через уровни доверенного доступа.
  5. Пример dual-use: анализ DNS-трафика ищет утечку в своём приложении, а те же приёмы годятся и для изучения обхода чужой защиты, и автоматический классификатор по тексту запроса их не различает.

Проверить свою возможность получения Daybreak на chatgpt.com/cyber: в аккаунте раздел Your eligibility.

ОграниченияНужны платная подписка, возраст от 18 лет и проверка личности; выполнение условий, по словам автора, не гарантирует нужного уровня доступа.

04Китайская шпионская группа с сентября ломала vCenter через

thehackernews.comприменяют

группа, которую связывают с китаем (раньше её звали UNC5221), с сентября ломала vCenter через zero-day, то есть дыру атаковали до того, как вышла заплатка. обход аутентификации с CVSS 9,8 давал админ-доступ, а через него тянули данные. ну пиздец, сентябрь уже прошёл. проверь версию vCenter и поставь исправление под CVE-2026-123890, если его ещё нет.

Разбор

Это уже вторая VMware-уязвимость, которую эта группа в этом году использовала как zero-day. По данным CrowdStrike, раньше группа через CVE-2026-41709 (CVSS 2,7, шкала критичности) в VMware ESX снижала видимость журнала аудита, чтобы её действия было трудно заметить.

  1. Вход был через zero-day в BeyondTrust Remote Support (CVE-2026-102764, CVSS 9,3): оттуда закрепились, перешли на внутренний Linux-модуль и подняли права до root.
  2. Баг в vCenter дал обход входа через протокол SRP-6a (обмен паролем без его передачи): утёк ключ сессии, и без пароля получили сессию administrator@vsphere.local.
  3. BONESAW на Go выгружает базу LMDB, перехватывает SAML STS и создаёт SSO-администратора; SAWSNAKE выпускает поддельные SAML-токены, поэтому MFA не спасает.
  4. Для закрепления включили SSH на vCenter через интерфейс управления VAMI запросом PUT /rest/appliance/access/ssh, а на ESXi добавили свой SSH-ключ в authorized_keys для root.
  5. Для связи поставили бэкдор LAZYBONES, который проверяет команды в Slack-канале, а BEARBONES слушает TCP-порт 33992.

Сверить версию своего vCenter с исправлениями: 9.1.1.0200, 9.0.2.0200 и 8.0 U3m; для Cloud Foundation — 5.2.5.

ОграниченияДля vCenter 7.0 исправление выдают только по запросу в Broadcom Support и при контракте на расширенную поддержку.

06В nginx с 2015 года сидела дыра: без входа можно выполнить код на сервере

xakep.ruдоступно

вот это уже серьёзно: в nginx нашли дыру CVE-2026-123007, через неё можно выполнить код на сервере без входа, но только если включён HTTP/2. баг сидит в открытом коде с релиза 1.9.5 от сентября 2015 года, то есть одиннадцать лет. если HTTP/2 на серверах включён, обновляться до исправленной версии надо.

Разбор

nginx стоит на входе и принимает запросы прямо из интернета, поэтому баг в нём сразу интересен атакующим. Сама по себе дыра не даёт root, но в связке с другими багами даёт.

  1. Xint добились RCE, имея лишь доступ к порту HTTP/2, а Wiz в тестах обошла ASLR.
  2. Root получили через отдельный баг в SCTP-подсистеме Linux, и даже внутри Docker-контейнера.
  3. Публичный PoC от Rapid7 на GitHub годится только против свежего Docker-контейнера на том же хосте, и нужно около 128 ГБ HTTP/2⁠-⁠трафика: при 300 Мбит/с это больше часа.
  4. Всего в новых версиях устранили 10 уязвимостей; пять из них — NGINX2Root, каждая по 9,2 балла CVSS 4.0, и каждая требует своих условий, от HTTP/2 и HTTP/3 до почтового прокси.
  5. По данным Censys, на 19 ноября 2026 года около 8,8 млн доступных из интернета инстансов NGINX потенциально оставались уязвимыми.

Сравнить версию своего NGINX с исправленными 1.31.9 и 1.30.7; для NGINX Plus — сборки 37.3.0.1 и 37.0.8.1.

ОграниченияОбычного reload недостаточно: старые воркеры продолжают обслуживать уже установленные соединения, нужен полный перезапуск сервера. Для веток NGINX Plus R34–R36 исправлений пока не заявлено. Эксплойт Rapid7 ограничен keep-alive-ограничением NGINX и узким сценарием.
